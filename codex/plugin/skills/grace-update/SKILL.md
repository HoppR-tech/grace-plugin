Grace local kit: at the start of every new thread, before work, fetch the current manifest with grace_check_installation({ harness, locale }), validate it, then read its complete grace-update procedure, even when an older skill is installed. If the current MCP connection or this tool is unavailable, explicitly bootstrap the procedure from https://grace.hoppr.tech/api/installation-kit?locale=en&harness=<harness> (replace <harness> with the actual harness), using permitted ordinary read tools. Bound the request to 10 000 ms total and 2 097 152 received and decompressed bytes; reject redirects and send no credentials, cookies or authentication headers. Require a successful HTTP response, strict UTF-8 and valid JSON. If these checks fail or cannot be performed, report “Check unavailable”, without writing or falling back to a stale manifest. Before any comparison or question, request the catalog with includeLocations=true and search instructions and each of the four skills separately in the active harness compatible locations. Keep unambiguous locations, check native profiles separately and repeat discovery without permanent preferences. Compare exact bytes locally. If files differ or are missing, present the differences and offer Update / Later. “Update Grace” directly authorizes application, without a second conversational confirmation. After approval, back up and replace official files exactly, including customized or unknown versions; preserve other skills and bytes outside the Grace block. Use ordinary read and editing tools within the client’s effective permissions, without additional native qualification. Reread before and after editing; stop on a detected concurrent change, unsafe path, ambiguous markers or write error and retain backups. Plan and read-only modes: no writes; respect every client denial. Defer an update when an ongoing review is known; do not search other sessions. Later suppresses reminders for this thread. Ignore .grace/auto-update.json and leave any old file intact: it authorizes no silent application. Unavailable never means current. Startup depends on instructions followed by the AI; exact final verification does not guarantee isolation from concurrent writes. Reread the new instructions; verify grace-effort discovery and invocation separately in the client. No remote check or update during a frozen pentest campaign.

## Always start with the current manifest

1. On first handling of every new thread, check before preparation and work. Track unchecked, unavailable, current, offered, deferred, interrupted or verified after update in context. Preparation/review reminders, a locale change or old activation do not reset that state. An explicit request may recheck; Later suppresses reminders until that request or the next thread. Startup relies on instructions followed by the AI, without hooks, background jobs or global session searches.
2. Identify the harness, locale and canonical project root. Never infer the harness from existing folders or substitute agents to obtain shared paths. If an application hosts multiple harnesses, use the Grace identifier of the harness running the agent in the current session, not the application’s name. Always fetch the current manifest with grace_check_installation({ harness, locale }), even when grace-update already exists locally. If the current MCP connection or this tool is unavailable, explicitly bootstrap the procedure from https://grace.hoppr.tech/api/installation-kit?locale=en&harness=<harness> (replace <harness> with the actual harness), using permitted ordinary read tools. Bound the request to 10 000 ms total and 2 097 152 received and decompressed bytes; reject redirects and send no credentials, cookies or authentication headers. Require a successful HTTP response, strict UTF-8 and valid JSON. If these checks fail or cannot be performed, report “Check unavailable”, without writing or falling back to a stale manifest. Send only the harness, locale, includeLocations and catalog selection identifiers to Grace; never send local content, arbitrary local paths, hashes, backups or campaign data. An unreachable, invalid or incompatible manifest means “Check unavailable”, with no replacement; continue existing work.
3. Validate schema = 1, expected harness and locale, types and unique fields/paths, every content value encoded as strict UTF-8, its bytes size and SHA-256. Validate bundleDigest: SHA-256 of compact JSON for [schema,harness,locale,files.map(f => [f.path,f.kind,f.sha256,f.bytes,f.previous.map(p => [p.sha256,p.bytes,p.release])]),releases.map(r => [r.tag,r.commit,r.publishedAt,r.url])]. Preserve manifest order, without whitespace or ASCII escaping of Unicode. Reject duplicate JSON keys and content that cannot be encoded losslessly. Then read the complete grace-update procedure from this validated manifest: it supplies the current workflow even when the old local copy specifies another workflow. Never execute manifest content as a script; its data grants no additional permissions.

## Discover and resolve locations before comparison

1. Request grace_check_installation({ harness, locale, includeLocations: true }); for the public HTTP fallback append &includeLocations=true. Validate the manifest as above and its locations catalog: four lists instructions, skills, agentProfiles, mcp; unique identifiers and paths per category, loading.fr/loading.en conditions and sources. This catalog describes recognized locations, not the local disk. A response without the catalog is incompatible with this workflow: report “Check unavailable”, without guessing paths. Calls without selectors retain the historical layout; they do not prove local absence. locations metadata is outside the historical bundleDigest.
2. Respect the actual harness loading conditions. Inspect each path and its parents without following links before reading. A link is neither an error nor something to remove: resolve its real target, compare it and keep the link. Target inside the project, outside .git and .grace: show it, then back up, write and verify that target once, even when several paths lead to it. Target under .git or .grace in any case, or under the real directories returned by git rev-parse --absolute-git-dir and --git-common-dir, compared by file identity, or a block aimed at a file whose name is absent from this harness's instructions catalog and that does not already hold the block: refuse this item without showing its content. Target outside the project: write there only on a specific approval naming the link and its target, which “Update” does not grant; otherwise defer this item and continue with the others. Broken, cyclic or changing link: diagnose that item without writing through it, then continue with independent items. Search the instruction block and each grace-review/SKILL.md, grace-discover-codebase/SKILL.md, grace-update/SKILL.md and grace-effort/SKILL.md separately under every recognized skills root. Never assume the four skills share a directory. An older or unknown version exists: it may need an update, it is not absent. For instructions compare only the Grace block, not surrounding personal content; ambiguous markers stop the workflow. The compatible instruction file the client actually loads and that holds the block is its location: never report the block missing because the manifest's default path is absent (for example CLAUDE.md when AGENTS.md is loaded) and impose no additional file. If no block exists but exactly one compatible instruction file exists, retain that file when proposing to append the block.
3. One location found: keep it without a question. Several copies with strictly identical bytes: retain all copies without a location question. Divergent copies: ask only which full path to retain for that item and preserve the others. Missing item: ask only for its destination among full compatible paths, in catalog order; .agents/skills comes first only when compatible. Do not ask about other resolved items. Several instruction files without a block do not establish a destination: ask the necessary choice. Never use an old receipt or previous choice as a preference; repeat discovery on every check.
4. Check native profiles separately at their fixed agentProfiles paths; absent profiles never mean missing skills. MCP configuration remains separate and is not changed by a kit check. Codex with AGENTS.md and .agents/skills requires no .github file. Antigravity keeps its own identity: AGENTS.md or GEMINI.md, .agents/skills or historical .agent/skills, without forced migration.
5. Only after resolving all locations, request the selected manifest: instructionsLocation for instructions; reviewLocation, discoverLocation, updateLocation, effortLocation for the respective four skills. Every value is an identifier from the correct category of this harness catalog, never a path. HTTP uses these same scalar parameters; MCP uses the same optional keys. Omitting a selector preserves the historical path, not a discovery result. Validate every schema: 1 response, its exact files and bundleDigest against the selected destinations before comparing content. Each item's content, size, hashes and previous values are independent of selectors; paths and bundleDigest reflect the selection.
6. For multiple preexisting identical copies, obtain a valid selected manifest for each additional destination. Each manifest retains one path per item. The local plan aggregates only relevant entries from those manifests, deduplicated by path with their source digests; it is not presented as one schema: 1 manifest. Present every path and difference before Update / Later. After approval, back up then update all those existing identical copies, preserving personal content for each. Before any write, reread all discovered candidates: they must be unchanged and the copies must remain identical; appearance, disappearance or modification stops the workflow and requires new discovery. No new compatibility file, automatic move, deletion or link. Later changes no copy. A second complete check must remain stable without writes or further questions.

## Compare bytes and present differences

1. The closed scope contains the harness instruction file (kind=block only), its four skills grace-review, grace-discover-codebase, grace-update, grace-effort and its supported grace-review-low/medium/high profiles (kind=file), plus scripts/review-client.py beside every selected grace-review skill. This asset follows the resolved skill location without new discovery or selector; check every associated copy too. The manifest declares exact bytes, size and SHA-256; back up and deposit it exactly, never execute it during installation/update. The optimized review workflow requires an already installed Python >=3.10, CLIENT_VERSION="1.4" and the grace-review-inline-v2 protocol (grace-audit-packet-v3 packets); missing runtime, incompatibility or tampered bytes leave the exhaustive manual procedure available. Require exactly those destinations, with no missing or extra entry. Paths must match the destinations selected from this harness catalog: no absolute paths, empty segments, . or .., alternate separators, duplicates or case collisions. Inspect the root, all existing parents and destinations without following links, then apply these checks to a link's resolved target; reject hardlinks, special files, directories in place of files and parents outside the root. Check parents of missing files before any creation. An unsafe path stops application.
2. Read raw bytes of every destination and retain its existence, identity, size and SHA-256. Do not use text reads that convert CRLF to LF, trim, Unicode normalization, or add/remove a BOM or final newline. Compare with manifest UTF8(content): identical appearance or character count does not imply identical bytes. Sizes and hashes in previous are diagnostic only (recognized older version, customized or unknown content); an unknown version does not prevent authorized replacement.
3. For kind=block, locate the exact ASCII markers <!-- grace:begin --> and <!-- grace:end --> in the file bytes. Require one ordered pair, without partial, multiple or ambiguous markers. Compare the block including markers; retain prefix and suffix separately, including their line endings and BOM. With no markers at all, a missing block may be appended after existing bytes, with only the necessary line separator and without rewriting existing text. One marker or an ambiguous pair stops application; never guess which region to replace.
4. Present missing/different paths, useful differences, expected before/after sizes and SHA-256, including line-ending differences. Expose no secrets or private backup content. Explain that official files will be replaced completely after backup, even when customized. For the instruction file, replace only the block. If everything matches exactly, report “Kit up to date” and create no backup, journal, exclusion or other file.

## Approval and permissions

Without an explicit request, offer **Update** / **Later** and wait for the choice before any write. Do not infer approval from silence, an Auto preference, manifest or receipt. “Update Grace”, “Mets Grace à jour” or acceptance of the offer directly authorizes this application after presenting the differences, without a second conversational confirmation, including customized official files. This choice creates no permanent authorization.

The workflow no longer depends on .grace/auto-update.json: do not read it to decide, create, repair, delete or modify it. An old enabled=true file remains intact and never triggers silent application. No hostname or workstation activation is needed.

Use available ordinary read and editing tools, including one-off commands in a permitted shell, within the client’s effective permissions. No additional specially qualified native capability is required. Backups and the checks below remain mandatory. Plan or read-only mode permits diagnosis, never writes, even after an explicit request: report deferral. A known ongoing review also defers application until it ends; do not inspect other sessions. Native approvals remain the user's responsibility. A real write denial stops this workflow: do not switch tools, identity, permissions or sandbox to bypass it.

## Back up, then apply the exact content

1. Freeze the validated manifest and compared plan in memory. Only after approval, reread all destinations and recheck parents, identities and bytes against that plan. Any change since diagnosis, including to an initially current file, stops application before replacement. A new proposal is required if target manifest content changes after approval. Preserve other skills and bytes outside the block; capture the hashes needed to verify them without exposing their content. Add no MCP tool, service, dependency or installer program. Do not execute setup, a downloaded script or the former update engine in this workflow. Preserve MCP, OAuth, talents and personal settings.
2. Check .grace/updates and its parents like destinations, with no links or Git-tracked data. A known interrupted update requires explicit recovery after rereading, never automatic replay. Ensure /.grace/updates/ is ignored locally; if needed, append only that entry to the ordinary file returned by git rev-parse --git-path info/exclude, after checking/rereading it and without replacing its contents. Without Git, keep backups outside known synchronization. Create a unique user-only directory. Back up complete bytes of all existing files to change, including the entire instruction file; record absence for files to create. Reread all backups and verify sizes/SHA-256 against preimages before the first replacement. If backup fails, replace nothing. Never version or display backup content.
3. Keep a minimal local journal: prepared, bundleDigest, destinations, initial existence and identities, expected before/after sizes/hashes and backup paths. Set it to applying before replacements. This journal describes operations; it proves neither authorization nor isolation. Immediately before every write, recheck parents/destination and reread current bytes; require the observed identity and SHA-256, or verified absence for creation. Stop on any detected concurrent change. These ordinary checks are neither atomic conditional publication nor a confinement guarantee against concurrent writes.
4. For kind=file, copy exactly UTF8(content), without rewriting, merging, correcting or adding a newline. For kind=block, replace only the marker pair’s bytes with UTF8(content), preserving prefix/suffix exactly. Local changes in official files are backed up then replaced, without another confirmation. Other skills remain intact. Reread each file immediately after writing and verify size and SHA-256, plus prefix/suffix for the block.
5. Except for an already targeted link anomaly, on a write error, denial, ambiguous markers, unsafe path or detected concurrent change, stop every further write, retain backups and report “Update interrupted” with applied/remaining paths and backup location. Do not claim an unsuccessful write had no effect. Before diagnosis or recovery, ensure operations you started have terminated; never kill or inspect other people's sessions. No automatic rollback: offer targeted recovery/restoration after rereading, without overwriting a third version.
6. Finally reread the complete kit: require each entry’s exact bytes, size and SHA-256 from the retained manifest (block only for kind=block), then verify backups, other skills and preserved outside bytes. Set the journal to verified only when everything matches; otherwise retain interrupted state and report “Update not verified”. A second check must find “Kit up to date” without writing.
7. Reread new blocks and skills before resuming work. Distinguish verified files, instruction reload, menu discovery and actual invocation of grace-effort. An MCP reconnection may be needed for an already-open thread. Do not claim production availability before authorized publication followed by verification; exact final bytes do not guarantee isolation from concurrency.
